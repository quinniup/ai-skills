# docs-template：团队文档模板

按固定模板产出文档。用户只需回答问题、提供材料，不需要自己打开或编辑模板文件。

## 可用模板

| 模板 | 文件 | 适用场景 |
|---|---|---|
| 研发技术设计方案 | [templates/tech-design.md](templates/tech-design.md) | 需求开发前的技术方案、详细设计、方案评审 |

用户的意图能对应到某个模板就直接用；对应不上时列出可用模板让用户选。没有合适模板时如实说明，不要临时编一个结构当成团队模板。

## 写作要求：言简意赅

文档是给研发评审和查阅用的，只写结论和事实，不写论述性的小作文。

- 能用图、表、列表表达的不写段落。确实要写段落时，一段不超过 3 句。
- 每条只写一个事实或决策，直接给结论。不写铺垫和过渡句，比如"本节将介绍""综上所述""值得注意的是"。
- 需求背景 1～3 句，目标逐条列出，有可量化的指标就写指标。
- 不复述需求文档，贴链接即可。不讲通用原理和常识，比如"引入缓存可以提升性能"。
- 改造类需求只写改动点和受影响的部分，不把整个系统重新介绍一遍。
- 不写空话。"保障系统高可用""充分测试"这类没有具体措施的句子，要么改成具体做法，要么删掉。
- 风险说明用表格，列为风险、影响、应对措施，每格一句话。

示例：

- ❌ 随着业务的快速发展，订单量持续攀升，现有订单查询逐渐暴露出性能瓶颈，严重影响了用户体验，因此我们亟需对其进行优化改造。
- ✅ 订单查询 P99 为 800ms（日均 50 万次），目标降到 200ms 以内。

## 工作流

### 1. 收集信息

用 AskUserQuestion 一次问清下面几项（已能从对话或仓库得知的就不再问）：

- **文档主题**：需求或功能名称，用作文档标题和文件名。
- **输入材料**：需求文档链接或内容、相关代码目录、已有设计文档、接口或表结构草稿。
- **改动类型**：全新系统 / 已有系统改造。改造时需要写清"原有设计 → 改动点"。
- **输出位置**：默认 `docs/design/<主题>-技术设计方案.md`；仓库已有文档目录时沿用其约定。

材料不足以写某一节时，先完成能写的部分，最后统一列出待补充项，不要每节都停下来追问。

### 2. 调研

- 读取用户给的需求材料和相关代码，弄清现有组件、调用链路、领域实体、表结构和配置。
- 接口、表结构、配置项以代码和实际 DDL 为准，不凭命名猜测。
- 外部链接无法访问时告诉用户，请对方粘贴内容。

### 3. 按模板填写

先完整读取模板文件，再按以下规则和上面的写作要求填写：

- **章节结构不变**：标题层级、顺序、名称与模板一致，不删、不改名、不合并。
- **不涉及的章节**写"不涉及"并附一句原因（例如"本次无存量数据，不涉及迁移"），不要留空或删掉。
- **模板里的引导语**（如"系统内组件的设计，组件之间的边界定义和组件之间的关系"）是填写说明，填写时替换成实际内容。
- **改造类需求**：组件架构设计、领域模型设计两节必须写出"原有设计"和"核心改动点"。
- **图**：系统交互图用 Mermaid `sequenceDiagram`，流程图用 `flowchart`，组件关系和领域模型可用 `flowchart` 或 `classDiagram`。
- **接口**：每个接口复制一份"xxx接口(新增)"小节，括号里标明新增 / 修改 / 废弃。请求参数和返回体用表格（字段、类型、必填、说明）加一段 JSON 示例。
- **数据库**：SQL 语句节放完整可执行的 DDL/DML；表结构节用表格列出字段；表关系可用 Mermaid `erDiagram`。
- **发布计划**：发布流程写清顺序（如 DB 变更 → 配置 → 服务 → 开关），回滚止血写清触发条件和具体操作。
- **不编造**：缺信息的地方写 `【待补充：需要什么信息】`，不要用看似合理的内容填充。

### 4. 交付

1. 写入文件前确认目标路径没有同名文件；有则询问覆盖还是另存。
2. 写完后对照写作要求通读一遍，删掉去掉也不影响理解的句子和空话。
3. 向用户说明：文件路径、写成"不涉及"的章节、全部 `【待补充】` 项及需要谁提供。
4. 用户补充信息后，在原文件上更新对应章节，同样遵守写作要求。

## 禁止事项

- 不改动模板文件本身；用户想调整模板时，提示对方修改本仓库的 `skills/docs-template/templates/` 并重新分发。
- 不把密钥、密码、内网凭据等写进文档；配置变更只写配置项名称和取值说明。
- 不自动 commit 或推送生成的文档。
